## Phase 8 — done 2026-10-19 (notes kept for later phases)
Same workflow (show every migration, wait for OK, commit + push each step, test in Chrome AR + FR). Decisions (user, 2026-10-18):
- **Plans:** the instant "child absent" in-app notification is in every plan (Basic too, it belongs to attendance); the daily alerts (and email, later) only with the `alerts` module (Pro / Premium).
- **Absence delay:** a parent is told 10 minutes after the absence is marked. Corrected within those 10 minutes (present or late) → nothing is sent. Corrected after it was sent → a short "correction" notification to the same parents.
- **Schedule:** Supabase `pg_cron`; dates and times from the database in Africa/Casablanca (never Node).
- **Channels:** in-app only for now (bell, list, Realtime). Design so email can be added later without touching what creates notifications: Resend, sending domain `tasyir.ma`. Parents who sign in by phone have no real email (`@phone.tasyiir.invalid`): email only to a real address.
- **Defaults** (each school's director can change them): too many unjustified absences = 3 DAYS with an unjustified absence in a calendar month → parent + surveillant; repeated lateness = 3 lates in 2 weeks → parent.
- Parent page: a school-entered justification ('mark') is labelled "Saisi par l'établissement" (`portal.absences.justification.bySchool`), as the staff list does by kind.

Steps: 1 notifications in the DB + absence notifications (10-minute delay, corrections, pg_cron) · 2 bell + notifications list + Realtime (school area + parent portal) · 3 alert rules + director settings page · 4 daily alerts (unjustified absences, repeated lateness) · 5 subscription expiring (director + platform owner) · 6 closing pass.

**Done**
- Step 1 — Notifications + absence notifications (migrations `phase8_notifications` + `phase8_notifications_grants`, no screen): `notifications` (recipient, type `absence` | `absence_corrected`, optional student, `data` jsonb = what the sentence needs, `read_at`); never the sentence itself — written when shown, in the reader's language; email later = a delivery of these rows. Grants: authenticated SELECT + UPDATE(read_at) only; RLS = own rows in own school; nobody inserts / deletes through the API. `absence_notices` (internal queue, no grant, no policy — advisor INFO accepted): the AFTER trigger `attendance_marks_absence_notice` (DEFINER) queues a mark that BECOMES absent (session within the school's last 7 days) with a snapshot (date, hours, subject) and `due_at = now() + 10 min`; when it stops being absent the row is removed and, if already sent, the same parents get `absence_corrected` with `data.now` = `late` (+ `minutes_late`) / `present` / `cancelled` (the session itself was deleted — the marks go after it; text "L'absence a été annulée par l'établissement" for step 2). Deleting a student sends nothing. `private.send_absence_notifications(p_now)` (pg_cron job `tasyiir-absence-notifications`, every minute) tells each parent account of the student (role parent, not deactivated, own password set), school active, attendance module on (`private.school_has_module(school, key)` = `has_module` for a given school); rows locked + skipped → never twice; an absence with no parent account is handled too. `public.run_absence_notifications(p_now)` = secret key only (tests pass now + 11 min; it also sends real due rows early on the DEV project). Tests: `phase8-notifications.mjs` (38; the teacher same-day case skipped on Sundays); full `test:actions` 1400 passed, 11 skipped (Sunday).

Surveillance = staff whose role has attendance.manage, not the director role (resolved by step 4). Grants: SELECT + UPDATE(enabled, threshold, window_days, recipients); RLS = own school AND `has_module('alerts')` AND alerts.manage (a Basic school sees / changes nothing). - Step 4 — Daily alerts (migration `phase8_daily_alerts`): pg_cron `tasyiir-daily-alerts` hourly → `private.send_daily_alerts_if_due()` acts only at 19:00 Africa/Casablanca (database clock) → `private.send_daily_alerts(p_today)`: schools active, modules alerts + attendance on, rule enabled. Unjustified absences = DAYS of the month (1st → p_today) with an absence not excused, ≥ threshold → told ONCE per student per month. Repeated lateness = lates in (p_today − window_days, p_today] AFTER the student's last lateness alert, ≥ threshold (same lates never twice). Excused (`private.mark_excused`) = an APPROVED justification covering the day ('days') or that mark ('mark'), or a PENDING one sent ≥ p_today − 7 (Morocco date of submitted_at): unreviewed for more than 7 days → counts again (user, 2026-10-19); rejected excuses nothing. Recipients (`private.alert_recipients`): parents = same as absence notices; surveillance = role with attendance.manage, key ≠ director (custom roles too); director = role key director; all active + own password set; one notification each. `alert_events` (internal, no grant / policy, advisor INFO accepted) = what was told: unique per student + month (absences) / per student + day (lateness), so reruns never repeat. Notification types `unjustified_absences` (data `month` "YYYY-MM", `days`) and `repeated_lateness` (`count`, `window_days`, `from`, `to`); list sentences in 3 languages (`notifications.unjustified|lateness`, month via `formatMonth()` — ar-MA, Latin digits); a parent's row → `/portal/absences?child=`, staff's → `/students/[id]`. Absences entered late for a past month are never alerted. `public.run_daily_alerts(p_today)` = secret key only. Tests: `phase8-daily-alerts.mjs` (37; picks its days from the calendar, skips when the year is too young; pending expiry tested by running at today + 7 / + 8 since submitted_at is always now()), page checks in `actions-notifications.mjs`. Role keys match `^[a-z_]+$` (no digits).
