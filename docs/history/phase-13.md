# Phase 13 — Fees + payments + receipts

Started 2026-10-30, built **before Phase 12** (user, 2026-10-30: PLAN numbering kept). No online payment.

## Decisions (user, 2026-10-30)
- Module key: the existing **`fees`** (already in the Premium plan, labels, home page card). Permissions **`fees.view`**, **`fees.manage`**, **`fees.cancel`**.
- Roles by default: director = view + manage + cancel; accountant = view + manage (no cancel); every other role nothing (the director can grant `fees.view` in Rôles). Parents: own children only, through RPCs that check `private.is_guardian_of_student()`; no direct table policy. Students: nothing.
- **Discounts are director-only** (`fees.cancel` to insert / update / delete; `fees.view` reads) and every discount change is written to `audit_logs` (trigger).
- Amounts in integer **centimes** (`bigint`). Percent discounts rounded to the **whole dirham**. Percents first, then fixed amounts, never below 0. A fixed discount comes off **each** charge it applies to: the UI says **"par mois" / "شهريا"** next to a fixed amount.
- Billing months editable per year, default September → June; due day default 5. One price per service (per route later, with Transport).
- Sibling discount set by hand (a "siblings found" hint from shared guardians in the UI).
- One receipt per student. Receipt numbers per **school year**, gapless, per school. Receipts never deleted, only cancelled with a fixed reason code (`bounced_cheque` / `entry_error` / `refund` / `other`) + text, who and when; no "bounced" state yet. Cancelling a payment returns its allocated amounts to unpaid.
- Payment above the whole year's balance refused; paying ahead allowed.
- `record_payment` takes a client **idempotency key** (unique per school): a double click never creates two payments. `paid_on` between today − 7 days and today (Africa/Casablanca, from the database), never in the future.
- `cancel_charge` needs `fees.cancel`. No UPDATE / DELETE grant on `payments` / `payment_allocations` for anyone.
- Every SECURITY DEFINER RPC: `set search_path = ''`, checks school + permission + module first.
- Receipt: amount in words FR + AR; reprints say **DUPLICATA**; cancelled receipts print with an "ANNULÉ / ملغى" band.
- Reminders: a manual button + an optional monthly rule; the push text shows no amount.

## Step 4 — payments (2026-10-30)
Migrations (DEV and production, same versions): `phase13_payments` (`20261030112502`), `phase13_payments_server_key` (`20261030125309`), `revoke_truncate` (`20261030140000`; on DEV applied by SQL + the version inserted by hand into `supabase_migrations.schema_migrations`, so DEV and production keep the same history).
- **Decisions (user, 2026-10-30):** allocation oldest due first by default (registration, months in order, tuition before services in a month), overflow to the next months; or the staff's own list `[{charge_id, amount_centimes}]` (this student's open charges, each ≤ its balance, total = the amount). Receipt label = `fee_years.receipt_prefix` (1–10 letters / digits / hyphens) + `-` + year label + `/` + 6 digits (`MDR-2026-2027/000123`, else `2026-2027/000123`), frozen in `payments.receipt_label`. Cheque: bank + cheque number required, cheque date optional. Payer name optional (≤ 100). Cancel note required only for `other`.
- **Tables:** `receipt_counters` (per year, `last_no`, bumped inside `record_payment`'s transaction: no gap, refused inserts use no number), `payments` (receipt no + label, amount 1 – 100 000 000 centimes, method cash | cheque | transfer with `payments_method_fields_check`, bank / reference / cheque_date, payer_name, note, paid_on, `idempotency_key` unique per school, `received_by` = `auth.uid()` only, cancel columns), `payment_allocations` (payment + charge + amount). Grants: SELECT only, for `authenticated` (fees.view) and `service_role` (follow-up migration: Supabase's default gave it ALL, and TRUNCATE fires no row trigger).
- **Never changed / deleted:** triggers `payments_guard` / `payment_allocations_guard` are SECURITY INVOKER on purpose (a SECURITY DEFINER trigger always sees its owner as `current_user`): a delete needs the table owner AND (`tasyir.fees_purge` = on, set by `reset_demo_school` for its transaction, or the school itself being deleted — FK cascades run as the table owner); an update needs the owner (i.e. `cancel_payment`) and may only set the cancel columns, once. `authenticated` has no grant; `service_role` gets `fees_payment_immutable` (and, since the follow-up, no grant either). A student or year with payments cannot be deleted (FK, no ON DELETE); a school can.
- **RPCs:** `public.record_payment(student, year, amount, method, paid_on, idempotency_key, bank?, reference?, cheque_date?, payer_name?, note?, allocations?)` → (payment_id, receipt_no, receipt_label, replayed); errors `fees_forbidden`, `fees_year_not_found`, `fees_student_not_found`, `fees_amount_invalid`, `fees_method_invalid`, `fees_cheque_details_required`, `fees_paid_on_invalid` (today − 7 → today, `private.school_today()`), `fees_nothing_due`, `fees_amount_above_balance`, `fees_allocation_invalid`, `fees_allocation_total_mismatch`, `fees_idempotency_conflict`; per-key advisory lock (the same key at once → one payment, the others replayed) and the per-student lock shared with the refresh; audit `fee_payment.record` (receipt, amount, method, student, paid_on, picked). `public.cancel_payment(payment, reason, note)` (fees.cancel): reads the student, takes the per-student lock, re-reads the payment FOR UPDATE, then checks it; reasons `bounced_cheque` / `entry_error` / `refund` / `other`; audit `fee_payment.cancel`.
- **Charges:** `private.fee_charge_paid` = allocations of non-cancelled payments. The refresh keeps a charge that has ANY allocation (cancelled payments included) — the agreed price stays, `cancel_charge` removes what is not owed. A `fee_years` update that changes neither months nor due day (e.g. the prefix) refreshes nothing.
- `reset_demo_school`: payments + allocations purged first (flag on / off around them), then `receipt_counters`.
- **TRUNCATE (separate item, user 2026-10-30):** `service_role` held TRUNCATE on 55 of 58 public tables (anon / authenticated none). `revoke_truncate` removes it from anon, authenticated, service_role on every public table and from postgres's default privileges in `public` (new tables start without it; `supabase_admin`'s default can only be changed by that role — we never create tables as it). Nothing in the app, tests, scripts, cron jobs or the demo reset truncates a public table (`record_payment` truncates only its own temporary tables). The owner keeps TRUNCATE.
- **Tests:** `scripts/rls/phase13-payments.mjs` (95, in `run.mjs`). Database-level checks (DEV, rolled-back transactions): as `authenticated` / `service_role` with `tasyir.fees_purge` on, delete / update / cancel-by-update refused (service_role TRUNCATE was accepted before the follow-up, refused after); the owner without the flag refused; the owner with the flag (demo reset path) and a school's own deletion go through; a new table created by postgres after `revoke_truncate` has no TRUNCATE for any API role.
